# Round 1 — Risk seat

**Choice: C, with R selected separately. Confidence: medium.** This is C as written, including its exact independent-review triggers and Human acceptance of missing mandatory assurance; I am not proposing a lighter fourth option. This is advice for subsequent specification, not adoption authority.

## Rationale

C reduces important present failure modes without making a new distributed evidence runtime the prerequisite for ordinary delivery. A preserves useful frozen obligations, isolated ownership, fail-closed cadence and fresh checks. However, the actual `code-execute/SKILL.md` ends by refusing an independent verifier because the final check “already proves the unit.” Its mandatory commands are comments and harness validation, supplemented by unit-named checks. Those checks cannot establish assertion adequacy. Keeping that refusal makes A's low migration cost an inadequate answer to a feature whose selected test passes while failing to assert the promised behavior. C explicitly changes that policy for money, identity, persistent destructive state, concurrency and external contracts, and requires the author to identify a plausible wrong implementation for routine obligations. Those are concrete improvements over A, even though they remain judgment-based. Sources: `.agents/skills/code-execute/SKILL.md`, “Final check” and “Anti-patterns”; proposal, “C's precise independent-review trigger.”

B addresses a real weakness C leaves: an agent can manually copy yesterday's successful output after modifying a relevant untracked configuration file. A correctly implemented runner with the proposed tree identity and negative controls should reject that. Nevertheless, B's hardest safety component is also unresolved: which tracked, untracked, generated and ignored inputs belong in the digest; how report blocks are excluded without excluding requirements; and how shell commands, selected counts and platform reporters are interpreted. A too-broad exclusion creates false freshness; too-narrow exclusions create repeated invalidation and pressure to override the gate. The proposal candidly defers the formal contract to a future specification. This is not evidence that B is unsound, but it is a significant additional implementation and maintenance surface before comparative benefit is known. Sources: proposal, “B's deterministic contract and honest limits,” “Tested-tree identity,” and “Required verification”; research `verification.md` explicitly reports fixture tests rather than comparative delivery outcomes.

Distribution makes that additional surface consequential. `src/setup/apply.ts` skips existing paths individually, so setup can add new references or scripts while preserving an old skill instruction file. `src/setup/skill-sets.ts` places the three execution skills in always-installed core. A consumer therefore cannot treat a newer package version as proof of a coherent workflow upgrade. Both B and C need the proposal's manual coherent replacement, backup and old-plan grandfathering, but B adds versioned executable interpretation to the possible mixed installation. C has fewer moving pieces to restore. Rollback by coherent folder backup or integration-commit revert is sensible and preserves feature work; it cannot recover time spent satisfying an unsuitable workflow. Sources: those implementation files; proposal, “Attribution, distribution, compatibility and rollback.”

R merits selection independently. Candidate verification, visible unavailable checks, stable findings and re-fetching head before posting reduce concrete false allegations, stale anchors and lost rereview history. The existing review already forbids fixes, thread resolution and merge and requires an explicit ask. R preserves those authority boundaries and does not import an automatic GitHub poster. Its benefit does not depend on B's runtime. Sources: `.agents/skills/code-review/SKILL.md`; proposal, “R: selected Judge practices.”

## Main risk if wrong and strongest objection

C can preserve the exact clerical failure that motivates B: an agent misclassifies an external-contract change as routine, records a plausible assertion review, then closes against stale command evidence. Downstream consumers receive an apparently disciplined result whose assurance is weaker than its paperwork suggests. Routine UI and requirement omissions also fall outside C's mandatory independence triggers. If these failures recur, the lower machinery cost is a false economy; B would deserve preference.

## Observable test

On one already-wanted bounded feature, introduce a controlled relevant untracked-config change after proof collection, without changing HEAD. Observe whether C's manual identity check invalidates the evidence before closure, then obtain fresh evidence. Predeclare the time budget and record interruptions and false positives. A stale PASS directly falsifies a central reason to accept C's manual assurance; one successful detection establishes feasibility only.
