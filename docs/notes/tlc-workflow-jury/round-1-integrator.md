## Rubric and rationale

I prioritize requirement fidelity and evidence integrity, subject to hard constraints on truthful authority and consumer compatibility. Within those constraints, practical cost and maintainability break ties. Review quality is a separately selectable improvement. No supplied experiment measures the relative outcome gains, so this ordering is a value judgment rather than a numerical ranking disguised as evidence.

**A:** The baseline has substantive controls, not merely aspirations: frozen obligation/proof pairs and nine dimensions in `.agents/skills/code-spec/SKILL.md` (“Hard gates”); vertical slices and wave stops in `code-plan/SKILL.md`; fresh command evidence, reconciliation, and opt-in commits in `code-execute/SKILL.md`. A wins on immediate cost and compatibility. However, execute's “Independent-verifier ceremony” refusal says final checks already prove a unit. That overstates what command success establishes. Keeping A preserves that avoidable blind spot and lacks the proposed source/capture authority and per-test assertion review. These gaps justify a bounded change even without a measured defect-rate claim.

**B:** B has the strongest specified mechanical integrity: selected-count evidence, stale-tree rejection, graph checks, and mandatory fresh adequacy judgment address different failure classes. Its explicit separation of structural checks from truth is sound (proposal, “B’s deterministic contract and honest limits”). It also preserves commit cadence and remote-action boundaries. But those benefits require implementing and maintaining five new scripts, a versioned executable contract, command/report parsing, content-identity policy, and runtime negative controls across consumer environments. Node >=22 exists in `package.json`; this establishes package feasibility, not portability to every standalone skill host. The packet's 57 passing instruction tests and upstream mutation fixtures establish neither comparative delivery gains nor recurring verifier value. The value of building the entire B system before one feature trial is therefore uncertain.

**C:** C captures the source, approval, proof-selection, baseline, capture/gesture, and author-adequacy improvements without that new runtime. Its exact risk triggers require independent scrutiny for money, authority, persistent data, concurrency, and external contracts; unknown classification blocks rather than silently downgrades (“C’s precise independent-review trigger”). Routine proofs still require an assertion and a plausible wrong implementation, providing an observable minimum beyond a green runner. This is the best current balance under `.agents/rules/yagni-strict.md`: improve the actual contract while withholding unproven gate infrastructure. I accept C's weaker mechanical enforcement explicitly; this vote does not claim its manual records equal B's deterministic rejection.

**R:** Adopt the whole selected subset. Baseline review already requires grounding and deduplication; R adds head-drift checking, visible unavailable checks, candidate verification, stable findings, and scoped official-source research without importing Judge's runtime or arbitrary structural blockers (proposal, “R”). Its late-material-finding allowance protects correctness while the nit cap bounds noise. These improvements have a smaller integration surface and do not depend on choosing B.

## Risk, objection, and observable test

The main risk if C is wrong is systematic author blindness: a superficially credible table could conceal empty selection, stale evidence, weak assertions, or capture divergence in routine work. Non-triggered changes can still cause serious failures. R cannot substitute for execution assurance because review remains ask-only.

The strongest objection is that C adds substantial documentation while entrusting its enforcement to the same agent whose mistakes it addresses. B may amortize deterministic checks and independent closeout more cheaply than repeated manual auditing.

Test this on one already-wanted, approved, non-triggered feature with two vertical units. Predeclare a verification-time budget; deliberately supply an empty-selection command and then change a tested input after evidence capture. Observe whether C rejects both before claiming completion, and whether an independent post-trial audit can trace a sampled obligation to a meaningful assertion. Record false claims, missed failures, and elapsed effort. A false PASS materially favors B; successful handling supports feasibility, not statistical superiority.

## Material policy issues

No fatal contradiction changes my vote. Two implementation clarifications remain material. First, the universal candidate sequence makes R depend on preparation STOP 03, although A+R is expressly valid; an A+R plan must omit irrelevant core preparation rather than invent dependency work. Second, baseline-red behavior must distinguish a reported pre-existing failure from unauthorized scope expansion: the proposal requires stopping, but the locked spec must define the Human disposition and resumed proof policy. Neither issue authorizes silently changing obligations.

Distribution remains consequential for C too: `src/setup/apply.ts` preserves existing files while adding missing paths, so coherent manual folder replacement and consumer backups are prerequisites, not optional polish. Confidence is medium because these sources establish concrete gaps and implementation burdens, while no controlled delivery comparison establishes which assurance level repays its cost.
