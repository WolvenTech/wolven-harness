# Round 1 — Proponent

**Choice: B for the bounded trial described in the frozen proposal; R selected independently.** This is a recommendation to prepare an implementation specification and measure feasibility, not permanent adoption or execution authority. I do not change B's package into a smaller fourth option.

**Rationale.** B best addresses two different gaps without confusing them: whether the intended evidence actually ran on the current tree, and whether its assertions support the requirement. The current `code-spec/SKILL.md` already requires obligation/proof pairs and nine-dimension landings; `code-plan/SKILL.md` already preserves vertical slices, explicit dispatch and wave gates. Preserving these avoids paying for a replacement planning system. But `code-execute/SKILL.md`, “Final check” and “Anti-patterns,” combines fresh command output with an explicit refusal of independent verification, even saying the final check “already proves the unit.” Repository validation and comment checks cannot substantiate arbitrary feature behavior. B's semantic adequacy pass challenges precisely that unsupported inference. Upstream `tlc-spec-driven/references/validate.md`, “Each check's test,” supplies a concrete method: inspect the selected assertion against the criterion and probe additional examples. B improves on upstream by retaining scrutiny of repair evidence rather than treating green commands as sufficient closure.

For evidence integrity, B's “Tested-tree identity, commits, and report-only changes” is the strongest part of the proposal. Freshness covers dirty product bytes, tests, configuration and captures, while bounded evidence blocks can change without invalidating themselves. This respects the actual `code-execute` cadence contract: uncommitted work remains possible and completion marks remain coupled to successful commits. The scripts would check structural relationships and observed executions; the proposal explicitly denies that they prove approval, independence or assertion quality. This division is more credible than adding only stronger prose.

A wins on immediate cost, compatibility and absence of new maintenance. The supplied 57 passing contracts establish that its current instructions are testable, not that delivery is effective (`decision-packet.md`, “Shared evidence”). C is a substantial alternative: it obtains source fidelity, baseline checks and explicit proof tables with less implementation and runtime burden. Its exact independent-review triggers are inspectable rather than discretionary. Nevertheless, routine selection and freshness remain manual, and a requirement outside those five categories can still be badly asserted. B's feature-level scrutiny and mechanical rejection of stale or absent evidence make it preferable for a bounded feasibility trial; there is no evidence to assert a measured accuracy advantage.

Delivery is plausible rather than free. `package.json` already requires Node >=22 and ships `templates`; `src/setup/skill-sets.ts` places the three execution skills in core. `src/setup/apply.ts` preserves existing paths, while `src/skills/install.ts` replaces differing selectable folders only after consent. Thus the proposal correctly requires coherent manual core replacement and grandfathering instead of assuming setup upgrades old consumers. Skill-local scripts respect `test/helpers/skill-contract.ts`'s isolated-folder link contract. Attribution and synchronized trees remain release obligations.

R earns a separate yes: unavailable checks, official-source grounding of external claims, head rechecks, stable finding identities and a five-nit inline cap improve auditability without importing Judge's posting runtime. Its late-material-finding rule appropriately favors accurate disclosure over an artificially final first round. These changes preserve the current review skill's explicit invocation and no-merge boundary.

**Main risk if wrong.** B becomes a maintained validator system whose parsing, reporter assumptions and digest exclusions cost more than the delivery failures it prevents. False reassurance from an incomplete identity set would be worse than an openly manual limitation.

**Confidence: medium.** The local policy gaps and compatibility constraints are directly supported; the claimed practical benefit remains unmeasured. `tlc-spec-workflows-and-judge/verification.md` reports upstream fixture results, explicitly excluding a comparative agent benchmark.

**Strongest objection and observable test.** Strict YAGNI favors C because this packet contains no demonstrated local failure requiring four new scripts. Test B on the proposal's already-wanted feature with a predeclared time budget and deliberate empty-selection/stale-tree negative controls. Require independent tracing of one criterion plus recorded assertion findings and repair overhead. A false PASS or exceeded budget without useful evidence argues against retaining B.

**Material contradictions / missing policy.** No fatal contradiction changes my trial vote. The “optional skill-local tools” wording must not permit a B run to claim mandatory gates without Node. The digest file set and cross-platform command/count contract remain unresolved implementation obligations, not established capabilities. The explicit Human decisions, including degraded assurance and trial budget, remain necessary; this vote supplies none of them.
